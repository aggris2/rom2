# `.256` sprite files

A `.256` file is a list of pictures, called frames, in up to 256 colours.
Units, objects, structures and equipment are all drawn from these.

Measured on every `.256` file in the `graphics.res` of the GOG release:
1,929 files. The 1,915 files with a palette hold 40,474 frames, and the
measurements of the codes below are over those. The 6 files without a
palette hold 96 more and decode by the same rules. All numbers are
unsigned 32-bit, low byte first.

Read by `tools/import/sprite256.c`.

## Layout

```
[ palette, 1024 bytes ]    only if the top bit of the trailer is set
frame, frame, frame ...
[ unused bytes ]           in 5 files
trailer, 4 bytes           the last 4 bytes of the file
```

## Trailer

The last 4 bytes are one number.

- Low 31 bits: the number of frames. Largest seen: 256.
- Top bit: set if the file starts with a palette (1,915 files). Clear if
  it has none and the frames start at byte 0 (6 files, all projectile
  arrows; their colours must come from somewhere else).

8 files are empty, 0 bytes long (cursors). They have no trailer.

## Palette

256 entries of 4 bytes: blue, green, red, and a fourth byte that is not
used (0 in 99.9% of entries).

The colour order was checked by rendering
`objects/bush1/sprites.256` and `units/heroes/archer/sprites.256` both
ways. Read as blue, green, red, the bush is olive green and the bow is
wood brown. Read as red, green, blue, the bush is teal and the bow is
blue.

## Frame

| Offset | Field |
|---|---|
| 0 | width |
| 4 | height |
| 8 | data_size: number of bytes of codes that follow |

Largest seen: 316 wide, 303 high. All but 4 frames have a width and height
that are multiples of 8.

## Codes

The frame is filled left to right, top to bottom. Each code byte has a kind
in its top two bits and a count `k` in its low six bits.

| Top bits | Meaning |
|---|---|
| 00 | the next `k` bytes are `k` pixels (palette indices) |
| 01 | skip `k` whole rows, that is `k * width` pixels |
| 10 | skip `k` pixels |
| 11 | never occurs |

Skipped pixels are transparent.

Measured over all 40,474 frames:

- Every frame's codes add up to exactly `width * height` pixels, and use
  exactly `data_size` bytes.
- No run of pixels crosses the end of a row.
- No pixel in a run has index 0. Transparency is always a skip.
- `k` is 0 in 1,493 codes, all of kind 00. They do nothing.

## Odd files

Five files have bytes left over between the last frame and the trailer:
`projectiles/goblin/arrow.256` and `arrowb.256` (8 and 11 bytes),
`interface/myitem.256` and `shopitem.256` (20 bytes), and
`interface/shopframe.256` (1,743 bytes). A decoder reads the number of
frames the trailer gives and ignores what is left.

## The `b` files: soft edges

Nearly every sprite file of a unit, an object, a structure or a
projectile has a partner whose name has a `b` before the ending:
`swordsman.256` and `swordsmanb.256`, `sprites.256` and `spritesb.256`.
There are 395 such pairs, and in every pair the two files have the same
number of frames.

A `b` frame holds the soft edge of the figure in the matching frame: the
pixels just outside its outline. Its palette is all black and is not
used. The pixels are indices into the palette of the main file, and the
game draws them half see-through, under the figure, which smooths the
outline.

Measured on all 59 units ROM2 imports, with each frame placed in the
middle of the unit's box: of 888,975 edge pixels, not one lies on a
pixel of its figure. That the edge is drawn at half strength comes from
an earlier extractor and from how it looks. It was not measured in the
original game.

## Not known

- Where the 6 files without a palette get their colours. The `.pal` files
  are the likely place.
